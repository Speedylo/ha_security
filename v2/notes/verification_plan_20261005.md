# Verification plan — every claim, on one frozen version of the code

**Written 2026-10-05, before the engineering cut-off and before any of it is run.** Younes asked for a
holistic test plan so that every claim the report makes is tested, using professional, methodical
strategies. This is that plan. It runs as a single campaign. Its findings are recorded in §11, and
any correction reaches the report as a dated pointer, never as a silent edit.

## 1. Why a campaign, and why now

Three facts make one necessary.

**Most headline figures were measured on code that has changed since.** The mediator changed on
4 and 5 October: record-before-act, the push loop, ownership recorded after a publish, the UDP
relay's new checks, and the flood cut-off. But the 31.5 µs mediation figure was last measured on
2 September. The adversary suite's paired arm was last run on 2 September. Compatibility, the
garbage-collector attack, entity visibility, footprint and durability were last run on 3 October.
Each of those figures is true of the code it ran on. Nothing yet shows it is true of the code the
report now describes.

**The project's own history says self-tests are not enough.** §7.27, §7.31, §7.43 and §7.44 each
found defects behind suites that all passed. Every time, the defect was found by real code, a
re-run, or a person using the system by hand. A plan made only of suites would repeat the
mistake those sections record.

**An examiner will reproduce from the README, not from our shell history.** Today's manual test
found two defects that no automated path could reach: the browser's onboarding and the browser's
`get_services`. The examiner's path, a clean checkout followed by the README commands, has never
been run end to end.

## 2. Principles

1. **Claim-driven, not test-driven.** The unit of work is a claim the report makes, not a test that
   exists. Every claim goes into a register (§3) with its evidence, the test that checks it, the
   commit it was measured on, and a pass criterion fixed *before* the run.
2. **One frozen version.** Everything runs on a single tagged commit, `verify-2026-10`, on a Pi whose
   environment is recorded (§4). A fix made during the campaign creates a new tag, and everything
   it can affect runs again on that tag (§8, regression).
3. **Criteria declared before running.** Same discipline as the predictions. Counts must match
   exactly. Sets must be equal (the same integrations fail, for the same reasons). Timings must
   fall inside a tolerance stated in the register before the run. A result outside its criterion
   is a finding. The criterion is never re-read to fit the result.
4. **Every protection has a control.** A security result is evidence only if the same attack
   succeeds when the protection is removed. That can be a paired unconfined arm (§3.5's standard)
   or a mutant (§6.3).
5. **Recompute, don't read.** Every number in the report is regenerated by script from raw result
   files, not copied from a summary line. §7.31.12 and pass 2 of Stage 5 both record a summary
   that disagreed with its rows.
6. **Vary the environment.** Repeat where conditions differ: a rebooted Pi, a fresh (A), logs on
   disk rather than tmpfs, and a different time of day for anything timed. §7.24.2's 96% → 17%
   was found that way.
7. **Independent eyes.** Some attacks and some checks must come from someone who did not write
   the code (§6.6), because tests written by the author share the author's assumptions.

## 3. Phase 0 — the claim register (`notes/claims_register.md`)

**What goes in it.** One row per claim, extracted mechanically and then checked by reading:

| Source | What is extracted | Rough count |
|---|---|---|
| Abstract | every figure and every verdict | ~25 |
| §7.5 | the 20 requirements (C1–C4, F1–F4, S1–S9, N1–N3) and their verdicts | 20 |
| §7.26.3 and later restatements | 19 threat verdicts, as they stand after §7.30.5 and §7.44.4 | 19 |
| §7.26.4 | Corno and Mannella's 11, eight mapped | 11 |
| Chapter 7 result sections | every number in a results table or a bold sentence | ~250 |
| Chapter 8 | §8.2's contributions, §8.6's limitations (claims of absence too), §8.7's "done" rows | ~60 |
| Chapters 5–6 | claims about the built mechanism ("the sandbox cannot …", "every decision …") | ~80 |

**Each row records:** ID; claim text; every place it is stated (abstract, Chapter 7, Chapter 8,
submission draft); evidence type — *measured*, *self-test*, *argued*, *cited* or *design*; evidence
file; commit measured on; test method (from §5–§7); pass criterion; result; status.

**Status values.** *Verified* (reproduced on the tag, within its criterion). *Qualified* (holds
with a narrower wording, and the report gets a dated pointer). *Withdrawn* (does not hold; the
report says so). *Argued* (no test is possible, and the report must say "argued"). An argued claim
written as a measured one is a finding, the C1 lesson of §7.28.

**Tooling.** `verify/extract_claims.py` pulls candidate rows: every sentence with a digit, a
percentage, a ✅/⚠/✗, or *"every"*, *"never"*, *"no"*, *"all"*. A person then accepts, merges or
discards each one. Effort: about a day, and it is the most valuable day of the campaign. It is
also the inventory phase R's rewrite needs anyway.

## 4. Phase 1 — freeze and record the environment

- Tag `verify-2026-10` and copy exactly that tree to a new directory on the Pi
  (`~/r2exp/verify/`). Do not use the working copy that has been synced piecemeal. Check by
  hashing that the Pi's tree equals the tag's.
- Record in `experiments/verify/environment.json`: kernel, Raspberry Pi OS release, Python
  versions (`ha314`, system), a hash of `pip freeze` for `ha314`, `platform-deps` and
  `houseA-deps`, the Home Assistant commit (`759e465`), filesystem types of `/tmp`, `$HOME` and
  every scratch directory, free memory and disk, and uptime.
- Reboot the Pi. Kill stale supervisors and sandboxes. Remove stale cgroups and temp directories
  by literal path. Run `house_a up --fresh`. Run preflight.
- Check that credentials are present (`house_a.token`, `pirateweather.key`, `trakt.json`). Trakt
  refresh tokens are single-use, so count the remaining runs before starting.

## 5. Phase 2 — regression, at every level

The levels run bottom-up, so a failure is found at the lowest level that can show it.

**L1 — mechanism (26 suites).** All `selftest*.py` on the tag, twice: once after a reboot, once
after the other phases, to catch state leaking between runs. Pass: 26/26 both times, every
suite's internal count equal to the count in its last committed log, unless a dated change
explains the difference.

**L2 — integration against (A).** `selftest_real_platform --restart`, `selftest_push`, and the
supervisor's household path (`experiments/flood/drive_demo.py`). Pass: every check, with (A)
restarted fresh beforehand.

**L3 — real integrations end to end.** All 13 subjects on the tag:
- `endtoend`: `scheduler`, `adaptive_lighting`, `thermal_comfort`, `powercalc`, `watchman`, on
  the stand-in, plus `thermal_comfort` and `adaptive_lighting` against (A) with `--push` and
  `--command`;
- `endtoend_egress`: `nordpool`, `smhi_brandrisk`, `regensburg_transport`, `pirateweather`,
  `dwd_weather`;
- `endtoend_local`: `midea_ac_lan`, `localtuya` against the fake devices;
- `endtoend_oauth`: `trakt_tv`.

Pass: each subject's verdict equals its committed result, with the same published entities, the
same decisions (op, target, allowed, clause) and durable records that reconcile. Live values
(prices, temperatures) are compared with the movement §7.31 already allows.

**L4 — golden-result comparison.** `verify/compare.py` diffs every new result JSON against its
committed predecessor, field by field. Exact fields must match exactly. Toleranced fields must stay
inside their tolerance. New and missing fields are listed. The output is the regression report;
nobody judges a re-run by eye.

## 7. Phase 4 — the strategies that find what the suites cannot

### 7.1 Re-derivation of every number

`verify/recompute.py` takes each register row that has a numeric claim and an evidence file,
recomputes the number from the raw records, and compares it with the text in every place the
claim is stated: abstract, Chapter 7, Chapter 8 and the submission draft. That catches both
arithmetic errors and copies that drifted apart, which is §7.31.12's and pass 3's failure mode.

### 7.2 Reproduction from a clean checkout, the examiner's path

On a second directory on the Pi, and ideally on a freshly imaged SD card: `git clone` at the tag,
follow `README.md` and each experiment's README verbatim, without using knowledge that is not
written down. Every command that fails, every step that is missing (such as the undocumented
`houseA-deps`), and every path that only works on this Pi is a finding. Pass: every "Run:" block
works as written.

### 7.3 Mutation testing of the enforcement points

For each security-relevant check, remove or invert it on a scratch branch and confirm that at least
one suite fails. A mutant that survives means a claim with no test behind it. The mutants:

| # | Mutant | Claim it protects |
|---|---|---|
| M1 | default policy allows instead of denying | S6 |
| M2 | identity taken from the request's `integration` field, not the socket | S1, T02 |
| M3 | clause match ignores the port | S4, F3 |
| M4 | `is_public` accepts RFC 1918 addresses | T10 |
| M5 | `is_lan` accepts public addresses (§7.43's exfiltration) | T10 |
| M6 | the address resolved at request time is not re-checked | T11 |
| M7 | the record is written after the act (§7.36.1) | S7, record-before-act |
| M8 | the hash chain or the MAC chain is not checked | S7 |
| M9 | the manifest is not re-read at registration | T12, §8.7 #14 |
| M10 | the subscription filter is bypassed | S3 |
| M11 | the cut-off counts nothing | T19 |
| M12 | a cut-off integration may register again | T19 |
| M13 | the seccomp filter returns ALLOW | S8 |
| M14 | the integration's directory is mounted read-write | C1, S8 |
| M15 | `/proc` is not a fresh mount | T15 |
| M16 | a command is accepted from a channel it was not sent to | §7.38, C7 |
| M17 | `lock.*` is accepted at parse | S5 |

Each mutant is a small, reviewable patch kept in `verify/mutants/`, so the result is reproducible.
Pass: 17 of 17 are killed. Any survivor gets a test and a dated note.

### 7.4 Negative controls for every positive security result

Five results are paired against an unconfined arm (T01, T04, T14, T15, T17). For every other
"demonstrated" verdict, the register names the control that would show the attack works without
the protection: a mutant from §7.3, or a paired arm where one can be built cheaply. Where neither
exists, the verdict is worded "demonstrated at the decision layer", as T10 and T11 already are.

### 7.5 Fault injection and robustness

Each of these is specified in advance (N3) and asserted, not just observed:

- (A) stopped mid-run, and a reconnect;
- a sandbox killed mid-request;
- the audit-log disk full, which must fail closed;
- a mediator restart during the push loop;
- a malformed frame;
- an oversized frame;
- a slow sandbox that never reads (§7.36's P7);
- the network gone during an egress run;
- the Pi's clock jumping.

Most already have a case somewhere. The work is to put them in one place, run them on the tag, and
add the missing ones (the full disk, and the clock).

### 7.6 Independent adversary

Someone who did not write the framework writes attacks from Chapter 4's register alone. **Younes is
the right person**, and doing it is also viva preparation: for each threat, try to defeat the
control from inside a sandbox, starting from a blank file. Examples: reading another sandbox's
channel, reaching the mediator's socket, finding the token in `/proc`, smuggling data through a
declared host, flooding with *varied* requests. Each attempt is recorded with its outcome. One
that succeeds is a finding. One that fails becomes a new suite case, written by someone other
than the framework's author.

### 7.7 Security and code review

Run `/security-review` and `/code-review` (high effort) over `framework/` at the tag. Then do a
manual read of the five files that hold every enforcement point: `mediator.py`, `manifest.py`,
`egress_shim.py`, `udp_relay.py` and `sandbox.py`. §7.43 found more by reading than by measuring.

### 7.8 Evidence integrity

- **Pre-registration:** for every predictions note, git shows it committed before the first
  result file it predicts. Checked by script from commit timestamps.
- **Secrets:** scan the whole git history for tokens, keys and the Trakt and Pirate Weather
  credentials (`git log -p` with patterns, plus a dedicated scanner).
- **Logs actually committed:** every result a README lists exists in git. This is the `.gitignore`
  `*.log` lesson.

### 7.9 Document consistency

- Extend `toc.py --check` to assert every count the prose states: suites (26), threats (19),
  demonstrated (15), requirements (20), references (29), predictions.
- Every `§` cross-reference resolves to a heading that exists.
- Every `[n]` citation exists in the bibliography, and every entry is cited.
- Abstract, Chapter 7, Chapter 8 and the submission draft state each shared figure identically.

### 7.10 Citations

Verify all 29 references against their sources: [18]'s venue, [25]'s clause numbers, [26]'s ISBN,
and the two standards awaiting verification in `rewrite_consolidation_backlog.md` §7. Record each
as checked, with the date and what was checked.

### 7.11 Acceptance: the human path

A scripted run through the browser, as Younes did on 2026-10-05:
1. log in;
2. see a confined integration's entities;
3. operate a switch;
4. trigger the flood;
5. read and act on the Repairs issue;
6. restart (A) and see the entities survive.

This doubles as the defence demo's rehearsal. Pass: every step works without touching a terminal,
apart from starting the supervisor.

## 8. Findings, fixes and regression

- **Findings log, §11 below.** One row per finding: ID, phase, claim affected, severity, evidence,
  resolution.
- **Severity.**
  - *Critical:* a security claim does not hold.
  - *Major:* a reported figure is outside its criterion, or an argued claim is written as
    measured.
  - *Minor:* wording, a stale count, or a README step.
  - *Note:* nothing to change.
- **Fixes during the campaign are allowed.** It runs before the cut-off. Every fix gets a new tag,
  and everything the fix can affect runs again on that tag: always L1, plus the measurements whose
  code path the fix touches, judged with `compare.py`. A fix is not done until its regression is
  green.
- **Report changes follow the project's convention:** a dated pointer beside the original text, the
  §7.5 verdict updated in place, and one new section, §7.45, recording the campaign and what it
  changed.

## 9. Exit criteria

The campaign is complete, and the engineering cut-off can be declared, when:

1. every register row is *Verified*, *Qualified* or *Withdrawn*, or is honestly marked *Argued*,
   and the report's wording matches its status;
2. no Critical or Major finding is open;
3. 26/26 suites pass on the final tag, twice;
4. every measurement in §6 is inside its criterion on the final tag, or corrected in the report;
5. 17/17 mutants are killed;
6. the clean-checkout reproduction succeeds;
7. `toc.py --check` and the consistency checks pass;
8. Younes's adversary attempts are recorded.
