# 8 Discussion

## 8.1 The results against earlier work

The results answer the question that the literature left open. Corno and Mannella (2022) showed that an integration can reach another integration's data through Python's memory management, and recommended stronger controls in the hub without building them. The garbage-collector result in Section 7.1 shows why controls inside the shared process would not have been enough: the attack succeeded under confinement too, and found nothing only because the credential had been moved into another process. Separation by process, rather than a permission check, is therefore what defeats it. Thingnes and Meland (2025) proposed a working prototype for Home Assistant, evaluated against Corno and Mannella's threats, as future research. Scored against those eleven threats, the framework addresses eight, five of them fully. The three it does not address all concern availability: delay, partial loss of service and physical damage.

The compatibility result is the part with no earlier counterpart. Declared permissions succeeded in browsers because the platform could require developers to adopt them (Barth et al., 2010), and the SmartThings defences relied on a vendor that could do the same (Fernandes, Paupore, et al., 2016; Jia et al., 2017). SandTrap showed that existing extensions can be confined without changing their code, but on a JavaScript platform and on selected cases (Ahmadpanah et al., 2021). The results of Section 7.2 measure the same property for Home Assistant across two samples of its catalogue: no integration that loaded unconfined failed to load confined. The obstacle Barth et al. identified, an ecosystem of extensions written to expect full access, therefore did not prevent confinement in these samples, although every integration still needed a permissions manifest, and in this project each manifest was written by hand.

## 8.2 How far the results can be trusted

The results rest on an evaluation that was itself tested. Before the engineering cut-off, every claim in the report, 153 in all, was registered with its evidence and a pass criterion fixed in advance, and then re-measured on one fixed version of the code. Of the 153, 119 held as stated, 27 held only in a narrower form, 5 rested on argument rather than measurement, and 2 were withdrawn, and each is stated in the form its evidence supports. The test suites were checked in turn by introducing 53 deliberate defects into the code, all but one of which were detected, the remaining one being equivalent to the original. The campaign and the work that followed recorded 63 findings, one of them critical, and none changed the verdict on any assertion.

Running real integrations was the most productive check. The platform's recommended way of making web requests needs a network feature that a new sandbox lacks, so the first real integration tested could not make a single request, although every purpose-built test had passed. A test integration is evidence only for the code it exercises, which is why compatibility was measured on unmodified integrations from the catalogue rather than on test cases written for the framework.

## 8.3 Limitations

Each result carries a bound. The attacks were all written within the project, and no independent tester has attacked the framework. The end-to-end set is limited to integrations whose setup needs no account or device beyond those the project could obtain or simulate. The memory budget is set against an average number of integrations per installation, because the platform publishes no distribution, and memory was measured at rest. All results come from one platform release on one device, and the cost of writing a manifest for each integration was not measured. Subject to these bounds, the project's contribution is, within the literature reviewed, the first evidence that Home Assistant's existing community integrations can be confined without changing their code or the platform, at a cost that ordinary household hardware can carry.
