# 4 Literature Review

Section 2 identified a missing mechanism: a way for an integration's permissions to be declared, enforced and recorded. This section asks whether such a mechanism already exists, in web browsers, on other smart-home platforms or in work on Home Assistant itself, and states what remains undone.

## 4.1 How the review was conducted

The review covers five bodies of work: permissions for browser extensions, the security of smart-home application platforms, research on Home Assistant and similar hubs, the confinement of existing extensions on other platforms, and software supply-chain attacks. Sources were found through Google Scholar, Semantic Scholar, OpenAlex and the main security conference proceedings, and by following citations forwards and backwards from the closest papers.

Because a review of this kind can miss recent work, a second, documented search covered December 2024 to October 2026, with its protocol written down before it ran. It found 758 records, 642 of them distinct. Of these, 590 were excluded on their titles and 52 were screened on their abstracts, and only one, discussed in Section 4.4, was kept as closely related. None builds or evaluates confinement of Home Assistant's integrations. Section 6.3 describes how the author checked this AI-assisted screening.

## 4.2 Permissions for browser extensions

The problem was first addressed in web browsers. Barth et al. (2010) found that Firefox extensions ran with the user's full privileges, so a bug in an honest extension could be exploited by a hostile web page. Of the 25 popular extensions they studied, 88% needed less than the full set of privileges. Their answer was a manifest in which each extension declares the permissions it needs, enforced by the browser, and Google Chrome adopted this model, which became the standard for browser extensions.

The idea of declaring an extension's permissions in a manifest is therefore established and is not claimed as new here. Barth et al. also point to the obstacle this project faces, however. Chrome could require developers to adopt the model because its extension platform was new, whereas Home Assistant's thousands of integrations already exist and were written on the assumption that they have full access.

## 4.3 Smart-home application platforms

A decade of research on smart-home applications, mostly on Samsung SmartThings, found the same problem of applications holding more authority than they need. Fernandes, Jung and Prakash (2016) analysed 499 SmartThings applications and showed attacks that included planting a backdoor code in a door lock. Several defences followed. FlowFence runs sensitive code in isolated modules that may only move data in declared ways (Fernandes, Paupore, et al., 2016); ContexIoT asks the user to confirm a sensitive action in the context in which it occurs (Jia et al., 2017); and Tyche groups permissions by risk, because unlocking a door is far riskier than locking it (Rahmati et al., 2018). This project's permissions follow Tyche in treating locking and unlocking as separate permissions.

These defences rely on conditions that Home Assistant lacks. SmartThings is run by a vendor, applications run in the vendor's cloud inside a restricted programming environment, and the vendor can require developers to change their code. Home Assistant is run by the household on its own hardware, integrations run inside the platform's own process, and their authors are volunteers whose code already exists. None of these defences therefore carries over directly.

## 4.4 Research on Home Assistant and similar hubs

The closest work studies hubs that are extended by plug-ins, which is exactly Home Assistant's case. Corno and Mannella (2022) proposed a threat model of eleven threats for such hubs and tested it on Home Assistant. One of their test integrations used Python's memory management to reach another integration's data and read or change it, which shows that integrations sharing a process are not separated at all. They recommended that the hub enforce more controls, but did not build such controls. Their later work let plug-in developers declare the network addresses they need, enforced by firewall rules on the home router (Corno & Mannella, 2023). That design shares this project's declare-and-enforce idea but acts only on network traffic, so it cannot stop an integration from reading the home's devices or calling the unlock action, neither of which leaves the hub as network traffic. Its declarations also come from the developers themselves.

Independent reviews reach the same conclusion. A systematic review of 713 papers named an insecure extension runtime and insufficient access control among the main security challenges for users of such hubs, and it proposed, as future research, a working prototype for Home Assistant evaluated against Corno and Mannella's threat model (Thingnes & Meland, 2025). GitHub Security Lab's audit of Home Assistant left community integrations out of scope while warning that they have complete access to the installation (GitHub Security Lab, 2023). The one closely related paper kept by the documented search, a 2026 threat-modelling method for smart homes, names integrations, including code taken from GitHub, as an attack vector and leaves their mitigation to the owner reviewing that code (Kulkarni et al., 2026). This project takes up the review's proposal: it builds such a prototype and scores it against Corno and Mannella's threats.

## 4.5 Confining existing extensions elsewhere, and supply-chain security

One system has confined extensions that already exist, on a different platform. SandTrap confines the JavaScript extensions of Node-RED, another automation platform, without changing their code (Ahmadpanah et al., 2021). It shows that confining existing extensions is possible, but it is built for JavaScript, whereas Home Assistant's integrations are Python modules that share the platform's own process, and it was evaluated on selected cases rather than across a catalogue of extensions.

Supply-chain research asks a different question: how hostile code reaches users in the first place. Ladisa et al. (2023) classify the routes by which it enters open-source software, including the compromise of a maintainer, the route later taken in the XZ Utils case (Przymus & Durieux, 2025). Its defences, such as signed releases, reduce the chance that malicious code is delivered, but none limits what the code can do once it runs. Supply-chain security and confinement therefore complement each other.

## 4.6 The research gap

Together, these strands locate the gap. Declared permissions are proven in browsers, but on platforms that could require developers to adopt them. Smart-home security research is mature, but it assumes a vendor-run platform. The problem is recognised on Home Assistant itself, and confinement has been recommended but not built, and the one mechanism that was built acts only on network traffic. No published work builds or evaluates confinement of Home Assistant's community integrations, and none measures how many existing, unmodified integrations still work once confined, which decides whether such a scheme could be used in practice. The project makes three contributions against this gap. The first is a measurement of which parts of the platform community integrations actually use, taken over two samples of the community catalogue, which shows what a permission system has to cover. The second is a confinement design for Python integrations that share the platform's process. Confining unmodified extensions is not new in itself, since SandTrap did so for Node-RED, but doing it for this kind of extension, without the cooperation of the platform's developers or the integrations' authors, is. The third is a measured trade-off between security and compatibility: the share of real, unmodified integrations that still work once confined, which no earlier work reports.

These claims rest on the absence of earlier work, which is the hardest kind of claim to establish, since unpublished work may exist and the platform's developers could build confinement at any time. If they did, the second contribution would lose its novelty, but the measurement and the trade-off would remain valid whoever built the mechanism. Section 5 describes the methodology the project followed.
