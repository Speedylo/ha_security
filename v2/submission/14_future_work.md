# 15. Future Work

The framework confines the integrations it was tested on, but several questions remain open. This section describes them in order of importance, beginning with the limits on what the results can show and ending with the changes that only the platform itself can make.

The most important next step is an attack by someone outside the project. Every attack in the evaluation was written by the same process that built the framework, and a line-by-line reading of the code found a route out of the sandbox that no test had detected. Attacks written by the builders miss what the builders did not imagine, so only an independent tester can show whether the security result holds against attacks the project did not foresee.

The second question decides whether the framework can be adopted at all. Integrations run without any change to their code, but each needs a manifest declaring what it may do, and no integration ships one today. Authors could add the manifest themselves, since it changes no code. A manifest could also be derived by analysing an integration's source, which shows most of the packages it imports and the platform components it uses, and a curated collection maintained alongside the community store could serve integrations whose authors do not respond. Comparing a derived manifest with a hand-written one would show which of these routes is practical.

Cameras are the clearest gap in what confined integrations can do. The bridge passes still pictures but not live video, so `frigate`, `eufy_security` and `tapo_control` lose their main use when confined. Carrying a video stream to an approved device on the home network would close that gap. The eight camera and image integrations have also not been run end to end, as the fifteen in Section 12 were, and running them would show whether their pictures reach the household as intended.

The evidence itself can be widened in three ways. Running a household's own integrations for several months would test the compatibility and cost results in daily use rather than in test runs. Repeating the compatibility runs on each new release of Home Assistant, and on other devices, would show whether the results survive the platform's changes, and automating those runs would make the check routine. The reproduction guide should also be followed on a freshly installed device, which has not yet been done. Beyond these, a study with real users would test whether the person approving a permission understands what it allows, an assumption the evaluation could not examine.

The resource limits are also incomplete. The framework bounds memory, processor time and disk space, but not the rate at which an integration reads and writes the disk or uses the network. On the reference device, the kernel's disk-rate control is available only through a step that needs administrator rights at installation, which would change the framework's position of running as an ordinary user, so the trade-off needs its own decision.

Two risks lie beyond what confinement can close. An integration may misuse a permission it was granted, such as unlocking a door at three in the morning, and it may send household data to a host it is allowed to reach. The framework keeps a record of every action an integration takes through the mediator, so the unlock and the connection to the host would both appear in it, although what was sent would not. Preventing either, however, requires judging the context of an action rather than its permission. A model trained on an integration's past actions could learn what it normally does and hold an unusual action for a person's confirmation, much as ContexIoT asks the user about the context of a sensitive action (Jia et al., 2017). Such a model should only ever delay or refuse an action, never grant one, so that the framework's bound still holds when the model is wrong.

The framework's record of each integration's actions could also help other households. Each run is recorded with a fingerprint of the integration's exact code, manifest and dependencies, so a household could share a short verdict on that version, such as how long it ran and whether anything was refused, while the record itself, which reveals when a home stands empty, stays in the house. Without a central authority, however, an attacker can create enough fake participants to manufacture a good reputation (Douceur, 2002), and a clean verdict shows only that an integration stayed within its declaration, so this would be a separate project.

The last change is not this project's to make. A permission check inside the platform's own process can be reached by the code it restricts (Corno & Mannella, 2022), so a lasting fix requires Home Assistant to place community integrations behind a process boundary itself. The platform could also let an account be limited to some devices, which would narrow the mediator's own access to the devices that installed manifests name. This project provides the evidence such a proposal would need: what confinement costs, what a declaration must express and which threats it closes.
