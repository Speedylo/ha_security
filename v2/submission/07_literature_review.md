# 7. Literature Review

Section 2 ended by identifying a missing mechanism: a way for an integration's authority to be declared, enforced and recorded. This section asks whether such a mechanism already exists, in comparable extension ecosystems, on smart-home platforms or in work on Home Assistant itself, and states what remains undone.

## 7.1 Scope and method

Five bodies of work bear on the problem: least privilege for browser extensions, the security of smart-home application platforms, extensible smart-home hubs, software supply-chain attacks, and the empirical measurement of extension behaviour. Searches covered Google Scholar, Semantic Scholar, OpenAlex and the ACM, IEEE, USENIX and NDSS proceedings, combining terms such as *smart home*, *plug-in*, *integration*, *permission*, *sandbox*, *least privilege* and *Home Assistant*, and were followed by forward and backward citation chasing. The review is narrative rather than systematic: the search was not registered in advance, inclusion was by judgement, and no second reviewer screened the results. Relevant work may therefore have been missed, and Section 7.6 states what would follow if it had. The four sources closest to this project [5], [15], [33], [25] were read in full.

## 7.2 Least privilege for extensions

The problem is not new, and it was first addressed in web browsers. Barth et al. [14] found Firefox extensions running with the user's full privileges, so that a bug in well-intentioned extension code became exploitable by a hostile web page. Of 25 popular extensions, 88% needed less than the full set of privileges, but 76% used unnecessarily powerful interfaces, which made those privileges hard to reduce. Their response, a declared permission manifest with privilege separation, was adopted by Google Chrome and became the standard model for browser extensions.

Two consequences follow for this project. The central idea, declaring an extension's authority in a manifest and enforcing it at run time, is established practice and is not claimed as new. Barth et al. also identified the obstacle that governs this project's difficulty, however: Chrome could require developers to adopt the model because the extension platform was new, whereas Home Assistant's 4,220 integrations [1] already exist and were written against an interface that presumes full authority. The precedent shows where to go, but not how to get there from an ecosystem that cannot be rewritten.

## 7.3 Smart-home application platforms

A decade of research on smart-home applications, conducted almost entirely on Samsung SmartThings, documented the same overprivilege on a different kind of platform. Fernandes, Jung and Prakash [34] analysed 499 applications and 132 device handlers, found design flaws that granted applications far more authority than they used, and demonstrated attacks including one that programmed a backdoor code into a door lock. The mechanisms that followed each improved the platform's permission model. FlowFence [35] runs sensitive computation in quarantined modules that enforce declared data flows; ContexIoT [36] identifies the context of a sensitive action and asks the user at run time; SmartAuth [37] reconciles what an application's description claims with what its code does; and Tyche [38] groups operations by risk rather than by function, because unlocking a door is not the inverse of locking it in risk terms. Tyche's observation carries directly into this project's manifest, which distinguishes `lock.unlock` from `lock.lock`.

The framing of this literature applies to Home Assistant, but its assumptions do not. Table 7.1 sets the two platforms side by side.

**Table 7.1 — Platform assumptions in prior work and in Home Assistant**

| | SmartThings, as studied in [34]–[37] | Home Assistant |
|---|---|---|
| Who operates the platform | A vendor, centrally | The user, on their own hardware |
| Where applications run | The vendor's cloud, in a language sandbox | In the platform's own Python process |
| Permission model for applications | A capability system, found over-permissive | None: user permissions exist, but code inside the process bypasses them [10] |
| Can applications be required to change? | Yes, through developer terms and review | No: authors are volunteers and the code already exists |
| Distribution | A store the vendor controls | A community store with no code review [6] |

Each mechanism above therefore relies on something Home Assistant lacks. Tyche requires no change to applications, but it requires the platform operator to implement a new permission framework; FlowFence requires applications written against its programming model; and SmartAuth requires a position in an app store from which to mediate installation. None transfers to modules that are imported into the platform's own process from repositories the platform does not control.

## 7.4 Extensible hubs: the closest prior work

A smaller body of work addresses hubs extended by plug-ins, which is the Home Assistant case exactly. Corno and Mannella [5] proposed a threat model of eleven threats for extensible smart-home gateways, validated on Home Assistant with three purpose-built integrations. Their validation was offensive: one integration walked Python's garbage collector to reach another's live object, then read its secret or altered its state. This result constrains any solution, because it shows that no boundary exists between integrations sharing a process, so a permission layer inside that process can be bypassed by the code it constrains. The authors recommend that "the gateway itself (and its APIs) should enforce more controls" and that plug-ins "should authenticate themselves" [5], but they do not build or evaluate such a mechanism.

Their subsequent work [15] applies the Manufacturer Usage Description standard [39] to the gateway, letting plug-in developers declare the network endpoints they need; the declarations are merged into one gateway profile and enforced as firewall rules on a router. The design shares this project's declare-and-enforce shape, but three properties bound it, each evident from the paper. Enforcement happens at the network layer, so reading every entity or calling the unlock service, which never becomes a packet, is not mediated. Merging all declarations into one profile means each plug-in's effective policy is the union of every plug-in's declarations. And the declarations come from developers, who, the authors acknowledge, could alter them, so a malicious author declares what the attack requires. The evaluation covered three integrations, two of them purpose-built. Mannella's doctoral thesis [33] consolidates this line of work, and none of the future work it lists proposes runtime confinement of plug-in authority.

Independent reviews reach the same position. Thingnes and Meland's systematic review [25] screened 713 papers and named "Insecure Extension Runtime" and "Insufficient Access Control" among eight challenges for users of extensible hubs. The solutions it found were suggestions or belonged to other platforms, and it proposed, as future research, "a proof-of-concept implementation for Home Assistant … evaluated based on the threat model introduced by Corno and Mannella" [25]. GitHub Security Lab's audit of Home Assistant [40] likewise declined to examine community integrations, while warning that they "will have complete access" to the installation. This project adopts the evaluation framing that the review proposes: its threat register is scored against Corno and Mannella's eleven threats in Appendix C (Table C.5), where eight are covered, five without qualification, and the three not covered are availability consequences, such as physical damage, that a software control on the gateway cannot reach.

## 7.5 Supply chain, and measurement as method

Software supply-chain research addresses how hostile code arrives. Ladisa et al. [13] taxonomise the routes by which malicious code enters open-source ecosystems, including the compromise of a maintainer, the route realised in XZ Utils [8]. Its countermeasures, such as signing, provenance attestation and reproducible builds, reduce the likelihood that a malicious artifact is delivered, but none bounds what an artifact does once it runs. Supply-chain hardening and runtime confinement are therefore complements, as review and confinement were in Section 2.

One methodological precedent supports this project's approach rather than its subject. Li et al. [41], in a 2025 preprint, measured interface usage across 2,562 Model Context Protocol servers to argue for privilege management in that ecosystem. Measuring what extensions actually use, and fitting a privilege model to the measurement, transfers directly to Home Assistant, where no such measurement had been made.

## 7.6 The gap and the contribution

Taken together, the five strands locate the gap precisely. Least privilege for extensions is understood and proven [14], but on platforms whose operators could require migration. Smart-home application security is mature [34]–[38], but it assumes a vendor-operated platform with a sandbox and applications that can be changed. The problem is recognised on Home Assistant itself [5], [25], [40], and confinement has been suggested but not built; the mechanism that was built [15] enforces at the network layer and merges every plug-in's declarations. Supply-chain work [8], [13] acts on arrival rather than on behaviour.

> No published work builds or evaluates runtime confinement of Home Assistant's community integrations, and none measures the compatibility cost of confining extensions that already exist and cannot be rewritten, which determines whether any such scheme can be deployed.

The gap is therefore constructive and empirical rather than conceptual, and the project claims three contributions against it. The first is an empirical account of the platform interfaces community integrations depend on, measured over two samples of the community catalogue, following the method of [41]. The second is a confinement architecture for an extension model that cannot be changed, whose novelty lies in the retrofit, enforcing declared authority on code written to assume it has none, without the cooperation of the platform's maintainers or the integration's author, and not in the manifest. The third is a measured trade-off between security and compatibility: prior work argues that confinement is desirable [5], [25] or that overprivilege is common [34], but none reports what fraction of real, unmodified extensions still work once confined.

The claim rests on an absence, which is the hardest kind of claim to establish. Unpublished work may exist, and the platform's maintainers could build confinement at any time. If they did, the second contribution would lose its novelty, but the first and third, the measurement and the trade-off, would remain valid whoever built the mechanism. Section 8 describes the method by which the project pursued them.
