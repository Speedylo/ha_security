# 13. Learning Strategies

## 13.1 Tackling complexity through targeted research

The hardest constraint in the project was found by reading rather than by building. Corno and Mannella showed that an integration can walk the Python garbage collector to reach another integration's live objects [9], and that single result ruled out every design that enforces permissions inside the platform's process before any code was written. Read less carefully, the paper would have suggested the obvious first design, a permission wrapper around the platform's core object, which would have been unsound in a way that no test written for it would have revealed. The strategy that followed was to read the closest prior work in full and to state its limits precisely enough that they became requirements.

The same strategy was applied to the platform, where a claim that mattered was checked against the source code rather than taken from documentation or memory. Measured that way, 91% of the platform's 1,482 shipped integrations depend on its helper layer, which reversed the planned design of a stand-in object and led to a real, minimal copy of the platform inside each sandbox. The check was also applied late, and it still paid. The threat model had stated that the platform offers no restricted credential, so the mediator was given an administrator's. Read against the platform's source during verification, the statement proved wrong, and the mediator now runs as an ordinary user. The lesson is that a claim about someone else's system is a hypothesis until it has been read in their code.

## 13.2 Building expertise through practical experimentation

Experiments were preferred to argument wherever a question could be settled by measurement, and each was designed so that its outcome could contradict what was expected. Every prediction was committed before the run that tested it, and Section 6 scores all of them: of the first eight, made before the project knew how the ecosystem behaved, six were wrong. Those failures taught more than the predictions that held. The least-installed integrations, for example, were expected to load less often than the most popular ones, and they loaded more often, a result that would have gone unremarked had the expectation not been written down first.

The second habit was to run every comparison twice, once confined and once unconfined, on the same device and platform release. The pairing corrected the project's own conclusions more than once, and the corrections ran in both directions: an integration charged to confinement turned out to be failing because of the test instance, and another charged to the platform turned out to work in both arms once that instance was fixed. Without the unconfined arm, either error would have been reported as a finding.

## 13.3 Independent troubleshooting and system adaptation

The most useful lesson from troubleshooting was that a test which cannot fail proves nothing, and it was learned three times. The first real integration run against a real service could not build an HTTP client inside the sandbox, a fault that every test suite had missed because the project's own test subjects never used the client helper that real integrations are told to use. A demonstration script used in every regression reported success whatever happened, so each of those passes could not have been a failure. And when the supervisor's ability to kill a misbehaving sandbox was deliberately removed, its test still passed, because the test integration stopped by itself as soon as it was cut off. A second test integration, one that refuses to stop, was written so that only the kill could end it.

Each instance led to the same adaptation. Every check now has a deliberate defect paired with it, a small change to the code that the check must detect, and 53 such defects were written and run against the suites. A check that does not catch its defect is treated as a missing test, not as a pass. The security review that found a route out of the sandbox through a shared terminal, which no suite had detected, showed that even this does not replace an adversary who did not write the tests.

## 13.4 Managing knowledge acquisition and technical breadth

The project required working knowledge of areas that rarely meet: Linux isolation interfaces, the internals of the Python interpreter, a large platform codebase, risk-management standards and the design of empirical evaluations. Three strategies kept that breadth manageable.

The first was to write each requirement, with the way it would be verified, before learning what was needed to meet it. Learning was then directed at questions the project actually had, and the evaluation could not be fitted to whatever the implementation turned out to do. The second was to prefer one mechanism understood completely to several understood partially. The framework uses only Python's standard library and the kernel's own interfaces, without a container runtime, which was slower to build but leaves every security property explainable down to the system call. Because the code was written with AI assistance, that explanation could not be assumed, so a curriculum was written to rebuild each mechanism from the kernel's documentation, without reference to the framework's code.

The third strategy was to keep a record that could correct its author. Text later found wrong was not rewritten but kept, with a dated note recording the correction, so that what was believed before each result arrived remained visible. That record, a working report of about 141,000 words, is also what made this submission possible: condensing it required deciding, for every result, what an outside reader needs in order to trust it, a skill the project exercised from its first measurement to its last.
