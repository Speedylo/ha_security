# Part 1 — The setting

## What Home Assistant is

Home Assistant ("HA") is free software people run on their own hardware — often a
Raspberry Pi in a cupboard — to control their smart home. It talks to lights,
locks, thermostats, cameras, alarms, energy meters. It is the open-source
alternative to Google Home or Alexa, and its selling point is that your data
stays in your house.

## What an integration is

HA on its own does not know how to talk to your specific brand of doorbell. That
knowledge lives in an **integration** — a small piece of Python code that knows
one device or one online service. HA ships with a couple thousand official ones.

When an official integration is not enough, users install community-written ones
through **HACS** (Home Assistant Community Store), an unofficial add-on store.
There are ~3,105 of them, written by hobbyists, reviewed by nobody.

## The security problem

Here is the part that matters. An integration is **not a separate program**. It
is a Python module that HA loads *into its own process* and hands a live object,
conventionally called `hass`, which is HA itself in memory.

That means a community integration for, say, a broadband quota meter has, by
construction:

- read access to every device state in the house — every lock, camera, motion
  sensor, and whether you are home;
- the ability to call any service — including `lock.unlock` and
  `alarm_control_panel.disarm`;
- read access to `/config/secrets.yaml`, the file where every password and API
  key you have given HA is stored.

Not because anyone granted it those things. Because there is no mechanism to
*not* grant them. There is no permission system. Installing a HACS integration
is trusting its author with your entire house, and this is not theoretical — in
January 2021 HA disclosed exactly this: custom integrations stealing files.

## What the project builds

Two pieces, and the names matter.

**The supervisor** — a trusted program that holds the keys to HA. Every
integration ships a **manifest**, a short file declaring what it needs:

```yaml
name: matomo
publishes:      [sensor.matomo_*]        # entities it may create
reads_entities: []                       # nothing in the house
calls_services: []                       # no actions
network:        [analytics.example.org]  # one host, no others
```

The supervisor enforces that on every single request. Anything not declared is
refused and logged. This is the same idea as phone app permissions — a torch app
that asks for your contacts gets refused — applied where it currently does not
exist.

**The shim** — this is the clever part, and it is the harder half.

The problem: the 3,105 integrations that already exist all begin with
`import homeassistant`. If you run one outside HA's process, that line fails and
the integration dies instantly. So you either rewrite all 3,105 (impossible) or
you make the import succeed.

A **shim** is a counterfeit library with the same shape as the real one. In
Python, `import homeassistant` just means "find a folder named `homeassistant`
on the search path and load it." Control the search path, control what gets
loaded. So the project puts a *fake* `homeassistant` folder first on the path.
The integration calls `hass.states.async_set(...)` exactly as it always has and
cannot tell the difference — but instead of writing into HA's memory, that call
becomes a message on a socket to the supervisor, which checks it against the
manifest.

The integration runs **unmodified**. Not one line changed. That is the whole
trick.

# Part 2 — What was done on 2026-08-13

Six jobs, in the order they happened. The first two were planned; the rest each
followed from what the previous one turned up.

| | job | why it followed |
|---|---|---|
| A | measure the whole HACS catalogue | the 200-repo sample was suspected of bias |
| B | run two more integrations end-to-end | one integration is an existence proof, not evidence |
| C | weight everything by real installed base | repo counts turned out to be the wrong denominator |
| D | generate the "cheap" constant symbols | to see how much of the gap was actually cheap |
| E | run against a real, unmodified Home Assistant | the central claim was unproven without it |
| F | measure the registry gap, then close it | E surfaced a difference that needed quantifying |

## Job A: measure the whole population

The project rests on a bet: *most integrations use only a small, shared slice of
HA's API, so a shim only has to counterfeit that slice.*

That bet had been tested on **200** repositories. The tool
(`hacs_api_surface.py`) downloads each integration and reads its source code
without ever running it — untrusted code is parsed as text, never executed —
recording every `homeassistant.*` name it imports.

A **symbol** is one such name: `DataUpdateCoordinator`, `SensorEntity`. Think of
it as one word of vocabulary the shim must know. The question "how big must the
shim be?" becomes "how many symbols must it implement?"

The tool was run across the **entire catalogue: 3,105 repositories, 3,075 parsed
successfully.**

## Job B: run two more integrations

There was **one** integration proven to run end-to-end. One is an existence
proof — it shows the idea is not impossible. It is not evidence about
*integrations in general*, because the one might have been easy.

Two more were added, chosen because the data said they were closest to working:
`abnvle/ha-matomo` (a web-analytics dashboard) and `aniolpages/ha-icqa` (a
Catalan air-quality monitor). For each: extract the real source untouched, write
its manifest, build a fake version of its cloud service so it can be exercised
without real credentials, and run it.

Both now work. **Three integrations run unmodified under enforcement — 69
permission-checked operations, zero wrongly denied.** `spike/run_targets.sh`
runs all three.

## Job C: weight everything by what people actually run

Every number in the project so far counted *repositories*. Home Assistant
publishes per-integration install counts, so counting repos turned out to be an
avoidable mistake — see Finding 6.

## Job D: generate the constant symbols

The project's cost thesis says the long tail of the HA API is constants, and that
constants are machine-generatable rather than hand-written. `spike/generate_shim.py`
reads HA's own source with `ast` and emits them, which *tests* the thesis instead
of asserting it. See Finding 7.

## Job E: run against a real, unmodified Home Assistant

Until this, the supervisor talked to a hardcoded Python dictionary pretending to
be a house, which left the project's central claim untested. A stock Home
Assistant now runs in Docker and the framework publishes into it. See Part 4.

## Job F: measure the registry gap, then close it

Running against real HA revealed that framework-published entities are not quite
the same objects a normally-installed integration creates. Measuring that produced
the sharpest single result of the day — and then a fix for it. See Part 5.

# Part 3 — The findings

## Finding 1: the deep one — a bug that n=1 could not reveal

This is the most valuable thing that happened, and it needs some Python
background.

### Background: dataclasses

A `dataclass` is Python shorthand for "a class that just holds fields":

```python
@dataclass
class Sensor:
    key: str
    icon: str = None
```

You can declare one **frozen**, meaning immutable — once built, it cannot be
changed:

```python
@dataclass(frozen=True)
class Sensor:
    key: str
```

Setting `sensor.key = "x"` on a frozen one raises an error. Frozen is generally
safer; mutable is more convenient.

### The rule that causes the trouble

Python enforces a hard rule about inheritance: **a frozen dataclass may not
inherit from a non-frozen one, and a non-frozen may not inherit from a frozen
one.** Mixing them raises
`TypeError: cannot inherit frozen dataclass from a non-frozen one`. The
reasoning is sound — if a mutable class could inherit from an immutable one, the
immutability guarantee would be a lie.

### Why this bites

HA has a base class, `EntityDescription`, that integrations subclass to describe
their sensors. The shim provided its own copy, declared **not frozen**, with a
code comment saying real HA does something fancier but this was a harmless
simplification.

It was harmless — with one integration. Then:

- **`andrews_arnold_quota`** (target #1) subclasses it with a plain `@dataclass`
  and then *modifies* the object afterwards, rewriting
  `entity_description.entity_id`. **It requires the base to be mutable.**
- **`matomo`** (target #2) subclasses it with
  `@dataclass(frozen=True, kw_only=True)`. **It requires the base to be
  compatible with frozen.**

Now trace the consequences:

| shim's base is… | target #1 | target #2 |
|---|---|---|
| not frozen (what the shim had) | works | `TypeError` |
| frozen | `TypeError` | works |

**There is no choice that runs both.** Not a matter of picking better — the two
requirements are logically incompatible under Python's rule.

### How real HA solves it, and what was built

Real HA uses a **metaclass** — a class that customises how other classes get
created. Theirs is called `FrozenOrThawed`, and the trick is genuinely elegant:
the base class is deliberately **not made a dataclass at all**. It secretly
builds a parallel frozen dataclass off to the side and delegates object
construction to it.

Why that works: Python's frozen/non-frozen rule only triggers when a *base class
is a dataclass*. If the base is not one, there is no conflict to detect — so a
subclass may be frozen or mutable, freely. The base then injects its fields into
each subclass so nothing is lost.

This was reproduced as `spike/shim/homeassistant/util/frozen_dataclass_compat.py`.
One wrinkle: HA's version uses `annotationlib`, a module that only exists in
Python 3.14+, and this project runs 3.12. That part was rewritten to read
annotations directly. Same observable behaviour, runs on the local interpreter.

Both integrations now work, and frozen descriptions correctly *reject* mutation
— so the shim is more faithful than before, not merely more permissive.

### Why this matters far beyond one bug

**A one-integration spike could not have found this.** With one sample, the
simplification looked free. It took a *second* sample to turn it into a
contradiction. The shortcut was not wrong-but-tolerated; it was wrong in a way
that was **structurally invisible** at n=1.

That generalises to every remaining shortcut in the shim. Each is currently
"fine" against three integrations. Some fraction are genuinely fine, and some
are silently incompatible with integration #4 or #12 in ways nothing in the
current evidence can distinguish.

This is the strongest argument for a specific engineering priority: **grow the
number of integrations actually executed**, because that is the only process
that surfaces this class of defect. It is also an excellent thing to tell an
examiner, because it is a *methodological* insight, not just a bug report.

## Finding 2: the sample was biased, and the correction is good news

The 200 repos were taken in catalogue order, which is roughly alphabetical. That
is why every near-miss repository in the old results started with `a`. This had
been flagged as a possible problem. It was a real one:

| pattern | full catalogue | 200-repo sample | drift |
|---|---|---|---|
| actuator (accepts commands) | **46.7%** (1,437) | 58.0% | −11.3 |
| **polling_sensor** (only reads data) | **24.8%** (763) | 15.0% | **+9.8** |
| sensor_other | 9.4% (288) | 13.5% | −4.1 |
| other | 8.0% (246) | 6.5% | +1.5 |
| local_discovery | 7.8% (240) | 6.0% | +1.8 |
| push_stream | 2.4% (75) | 0.5% | +1.9 |
| oauth_cloud | 0.8% (26) | 0.5% | +0.3 |

**Polling sensors — the chosen target — are a quarter of the catalogue, not
15%.** In absolute terms, 763 real integrations rather than the ~285 the old
percentage implied.

Read on its own, this strengthens the weakest scoping argument. "I support one
pattern" sounded like a toy restriction at 15%. At 24.8% and 763 real programs, it
looks like a defensible engineering scope. Actuators (46.7%) are still the larger
group and still where the danger lives — a malicious *sensor* leaks data, but a
malicious *actuator* opens the front door.

> ⚠️ **Read Finding 6 before using any of these percentages.** Counting
> repositories turned out to be the wrong measure entirely. Weighted by how many
> people actually run each integration, polling sensors are **10.6%**, not 24.8%,
> and actuators are **64.8%**, not 46.7% — which points the opposite way from the
> paragraph above. Both numbers are correct; they answer different questions, and
> the install-weighted one is the honest answer to "how much of the real world is
> this?"

## Finding 3: the concentration bet held up

This was the thing that could have killed the project, so it is worth stating
plainly.

The bet was that a handful of symbols covers nearly everything. On 30
integrations, that could easily have been an accident of small numbers. On 763:

| symbol | appears in (n=763) | sample said |
|---|---|---|
| `DataUpdateCoordinator` | 98.7% | 100% |
| `HomeAssistant` | 98.2% | 100% |
| `ConfigEntry` | 96.7% | 97% |
| `SensorEntity` | 93.8% | 93% |
| `CoordinatorEntity` | 93.8% | 93% |
| `UpdateFailed` | 77.3% | 90% |
| `AddEntitiesCallback` | 73.0% | 80% |

The head is slightly less dominant than the sample said — the sample's two
"100%" entries were artefacts of having only 30 data points — but the **shape is
unchanged**. A small core still reaches a large share of the population. Every
downstream decision resting on this survives, now on 763 integrations instead of
30.

## Finding 4: two ways the coverage metric was misleading

The headline compatibility number came from asking: *does this integration
import everything the shim provides?* Two problems, both found on 2026-08-13.

### 4a. Hidden constants made it look better than it was

The measurement tool has a flag, `--exclude-trivial`, that ignores "cheap"
symbols — constants, unit names, type aliases — on the reasoning that they are
trivial to implement. The 200-repo dataset was built with it.

But **a missing constant still breaks the import.** "Cheap to write" and "not
needed" are different claims. `ha-icqa` was recorded as missing exactly one
symbol; when it was run, it failed on
`CONCENTRATION_MICROGRAMS_PER_CUBIC_METER` — a constant the dataset had never
counted.

So the measured gap understated the real gap. Not catastrophically — these *are*
cheap — but any published figure must state which flag produced it.

### 4b. Import success is not an upper bound on compatibility

The docs said import-cleanliness was an **upper bound** — i.e. "at most this
many could work." That claim is wrong, and `ha-matomo` disproves it: **it runs
end-to-end while still counting as one symbol short.**

Why? The missing symbol lives in `config_flow.py`, the module that draws the
setup wizard when a user first adds the integration through the UI. It runs
once, at installation, and never again. Nothing during normal operation touches
it. Missing a symbol there does not stop the integration from working.

So the metric fails in **both** directions:

- **Over-counts:** an integration imports everything, then dies at runtime on
  behaviour the shim does not reproduce — exactly the `current_entry` bug found
  earlier.
- **Under-counts:** an integration is missing symbols that sit on code paths
  that never execute — `matomo`.

It is not a bound in either direction. It is a **proxy**, useful for one job
only: ranking what to build next. The real compatibility measure is
*integrations actually executed* — which is 3, and which is why Job B mattered
more than Job A.

### 4c. A practical trap in the tooling

`shim_coverage.py` must be run under `../.venv/bin/python`. Run under the system
interpreter, `aiohttp` is missing, two shim modules fail to import, and the
scorer reports 180 names and 0/30 — while its warnings go to stderr and the
headline numbers print just as confidently. Worth hardening before those numbers
are quoted anywhere.

## Finding 5: the honest bad news — the cost estimate tripled

A **coverage curve** answers: "if I implement the N most popular symbols, how
many integrations can run?" It is how the size of the shim gets decided.

Measuring behavioural symbols only (excluding the generatable constants), across
all 763 polling sensors:

| behavioural symbols implemented | integrations fully covered |
|---|---|
| 30 | 15.2% |
| **51** | **25%** |
| 80 | 33.9% |
| **120** | **46.1%** (352) |

**50% is not reached within 120 symbols.** The sample had said ~83 symbols would
reach 50%. It does not.

This is now the third estimate of this quantity, and each revision came from
more evidence:

```
~15 symbols    (initial guess)
~83 symbols    (200-repo sample)
>120 symbols   (full catalogue)      <- each correction moved the same direction
```

Three estimates all revised upward is a pattern worth noticing: every time the
question was examined more closely, the job got bigger. That is a reason for
caution about any remaining unmeasured estimate in the plan.

### Why this does not sink the project

Two things stay true:

1. The head of the distribution is still steep — a small core still reaches a
   substantial minority quickly (25% of 763 integrations is ~190 real programs
   at 51 symbols).
2. The expensive tail is dominated by **generatable** material — units, enums,
   selector definitions — that a script can produce from HA's own source, rather
   than hand-written logic. The current top blockers bear this out: `util.dt`
   (blocks 257), the `selector` family (129 and below), `binary_sensor` enums
   (150).

What it kills is the claim *"most integrations run unmodified."* What survives
is *"a small hand-written core plus a generated constants layer runs a measured,
honestly-reported fraction."*

That is a weaker sentence and a stronger position. The advisor is a **security
auditor** — someone whose profession is finding the gap between what a system
claims and what it does. A curve that moved against you, presented as a curve
with its methodology, is far more credible than a single flattering percentage.
Stated limits are an asset with that audience.

## Finding 6: every number so far used the wrong denominator

### The problem with counting repositories

Findings 2 and 3 counted **repositories**: 3,075 integrations, of which 24.8% are
polling sensors. That treats every integration as equally important.

It is not a reasonable assumption. Some HACS integrations are installed on tens of
thousands of systems; many are installed on three. Counting repositories says a
project used by 43,601 households and one used by a hobbyist and two friends
matter the same amount.

### The data exists

Home Assistant asks users to opt in to anonymous analytics, and publishes the
results — including **per-integration install counts for custom integrations** —
at `analytics.home-assistant.io/custom_integrations.json`. It is keyed by
integration *domain*, which is exactly what the surface tool already records, so
the two join directly: 1,770 of 3,075 integrations matched, **1,064,724 installs**
in total.

*(Caveat for the report: this is opt-in telemetry, so it is a lower bound and a
relative measure, not a census. It is still the only public signal of real-world
use, and vastly better than assuming uniformity.)*

### What it changes

Everything, roughly:

| pattern | by repo count | **by installed base** |
|---|---|---|
| actuator | 46.7% | **64.8%** |
| polling_sensor | 24.8% | **10.6%** |

**Polling sensors — the chosen scope — are a tenth of what people run, not a
quarter of the ecosystem.** Actuators are nearly two-thirds.

Installs are also extremely concentrated:

```
top  10 integrations = 25.9% of all installs
top 100 integrations = 69.6%
top 200 integrations = 82.3%
```

100 integrations covering 70% of real-world usage is a tempting target. The catch:
those 100 are 59% actuators, and against the shim as it stands **exactly 1 of them
imports cleanly**, with a median of 22 missing symbols each. Popular integrations
are popular partly *because* they do more, which means they import more.

### What to do with it

Use installs as a **weighting**, not as the scope. Keep the pattern boundary — it
is what makes the API surface finite — but pick *which* integrations to target by
install count. Within polling sensors, the top 20 are 52% of all polling-sensor
installs, and several are already reachable:

```
1,569 installs   0 symbols missing   MarcoGos/kleenex_pollenradar
1,473 installs   0 symbols missing   delphiki/hass-tarif-edf
1,718 installs   1 symbol  missing   jonandel/ha-hildebrandglow-dcc
```

"Runs integrations installed on thousands of real systems" is a far better claim
than "runs three integrations", for the same effort.

## Finding 7: the constants really are generatable — and it barely helped

### The thesis being tested

Finding 5 said the tail of the API surface is dominated by *constants* — unit
names, enums, configuration keys — which are data, not logic, and so could be
generated from HA's source rather than written by hand. That was an assertion. Job
D turned it into a script.

`spike/generate_shim.py` downloads Home Assistant's source, parses it with `ast`
(**never importing or executing it** — the same discipline the surface tool
applies to untrusted integrations), and emits shim modules. It produced **469
constants and 93 selector classes**, taking the shim from 350 to **814 importable
names**.

So the thesis holds: the tail *is* generatable, it took an afternoon, and it will
regenerate for free on every HA release.

### Three things it turned up on the way

- **Home Assistant generates these too.** Since version 2026.8, `Platform` — the
  most-imported constant in the whole catalogue — lives in
  `homeassistant/generated/entity_platforms.py`. Upstream reached the same
  conclusion independently, which is a good citation for the report.
- **HA 2026.8.1's `helpers/selector.py` does not parse under Python 3.** Line 621
  is `except vol.Invalid, vol.MultipleInvalid:`, which is Python 2 syntax. The
  generator now degrades to line-based extraction rather than crashing. *Surprising
  enough to verify independently before repeating.*
- **A latent bug in the supervisor**: verifying an empty audit log raised
  `UnboundLocalError`. Found because a run failed; fixed.

### The result that matters

| | before | after |
|---|---|---|
| importable names | 350 | **814** |
| polling sensors importing cleanly | 9.4% | **12.3%** |
| median symbols missing | 6 | **4** |
| share of installed base | 0.8% | **1.2%** |

**Generating every constant and selector moved import-cleanliness by three
percentage points.** The thesis was true and the conclusion drawn from it was
wrong: the constant tail was a *smaller part of the problem than assumed*.

Look at what blocks the 100 most-installed integrations now:

```
50  binary_sensor:BinarySensorEntity     36  select:SelectEntity
50  helpers:entity_registry              33  number:NumberEntity
49  switch:SwitchEntity                  30  restore_state:RestoreEntity
41  button:ButtonEntity                  27  event:async_call_later
41  util:dt                              23  storage:Store
```

Almost all **behavioural** — entity platforms and stateful helpers. None
generatable. And `switch`, `button`, `select`, `number` are *actuator* platforms,
which loops straight back to Finding 6.

A greedy search makes the shape clear: implementing whole modules one at a time,
always choosing the one that unblocks the most installs, reaches only **5.8% of
the installed base after twelve more complete modules**. The curve is flat because
*every* import an integration makes must be satisfied before it runs at all.

# Part 4 — Running against a real Home Assistant

Everything above concerns whether integrations *can* run under the framework. This
part concerns whether the framework works against Home Assistant *as shipped* —
which is the project's central claim, and until today it was untested.

## Why it mattered so much

There is a sharp difference between two projects:

- **"If Home Assistant were redesigned to be secure, here is how."** Free to
  write. Nobody has to adopt it. Worth little.
- **"Home Assistant does not need to change; this can be bolted on today."** A
  *retrofit*. Much harder to dismiss.

The design has always been the second — the supervisor sits *beside* HA and talks
to it through the REST API HA already exposes to any client with a token. But the
supervisor had been talking to `DEFAULT_HOUSE`, a hardcoded Python dictionary of
six fake entities. **A claim about real Home Assistant cannot be supported by a
dictionary.**

## What was built

```bash
./ha_docker.sh up      # stock ghcr.io/home-assistant/home-assistant:2026.8.1
./ha_onboard.py        # headless onboarding, mints a long-lived token
./ha_seed.py           # give it locks, a camera, a device tracker
HA=1 ./run_targets.sh  # three unmodified integrations publish into it
```

Nothing about HA is modified: the official published image, no patches, no custom
components mounted, no configuration edits.

One detail worth knowing: HA normally insists on a **browser wizard** before it
issues any credentials, which would make the whole thing a manual step and
therefore unreproducible. It exposes the same wizard as a REST API, so
`ha_onboard.py` drives it headlessly and then mints a long-lived token over the
WebSocket API (the only route HA offers for that).

## Result

All three unmodified integrations publish into the live instance: **25 entities**
with correct units and friendly names, sitting in HA's own `/api/states` next to
its native `sun.*` sensors.

The adversarial probe re-run against a real house is much more convincing than
against a six-entry dictionary:

| attempt | stub house | **real HA** |
|---|---|---|
| read undeclared `lock.front_door` | blocked | **blocked** |
| enumerate the whole house | 2 of 8 returned | **2 visible, 41 withheld** |
| call `lock.unlock` (confused deputy) | blocked | **blocked** |
| exfiltrate to undeclared host | blocked | **blocked** |
| read a host file | ALLOWED | **ALLOWED** (unchanged) |

## The comparison that makes it a result rather than a demo

A demo shows something working. A *result* shows a controlled comparison. So the
same operations were run with the same token, used the way an ordinary in-process
integration uses `hass` today:

| | baseline HA | under the framework |
|---|---|---|
| `lock.front_door` | readable (`'locked'`) | **denied** |
| entities enumerable | **43** | **2** |
| privacy-relevant entities exposed | 5 | **0** |

Four commands reproduce it. That is the shape every security claim in the
evaluation chapter should take.

## A design point worth keeping

The switch from stub to real HA is a **backend swap, not a policy change**.
`ha_backend.py` holds both behind one interface, and `supervisor.decide()` — where
every manifest check lives — is byte-identical either way. Every check still runs
*before* the backend is touched.

That is not tidiness. It is what makes the two columns of the probe table
comparable: the policy under test is provably the same code.

# Part 5 — The registry gap: measured, then closed

Running against real HA immediately raised a question that a stub could never have
raised: are the entities the framework publishes *really the same* as the ones a
normally-installed integration creates?

## The concepts you need

Home Assistant keeps three registries, and they are what make an entity a
first-class citizen rather than a floating value:

- **Entity registry** — a row per entity holding its stable identity: a
  `unique_id`, which integration owns it, whether the user renamed, hid, disabled
  it, or assigned it to a room.
- **Device registry** — physical or logical devices, so related entities group
  together in the UI.
- **Config entries** — a user-visible configuration you can reload, reconfigure,
  or delete from the UI.

Posting a value to `/api/states` creates *a state*. It does not create any of
those.

## How it was measured

Not by guessing at what might be missing — by running **the same integration two
ways at once** against the same live instance:

```bash
./ha_compare_setup.sh              # matomo installed natively AND via the framework
./registry_gap.py --restart-test
```

`matomo` was installed into HA's own `custom_components` and configured through its
real config flow, *and* run outside HA under the supervisor. Both publish 15
entities. The only variable is the delivery path.

## Result 1: no registry row at all

Not a sparse row — **no row**. So every identity field is *structurally
unavailable*, not merely unset:

| field | native | framework (REST) |
|---|---|---|
| `unique_id` | `matomo_1_actions_month` | unavailable |
| `config_entry_id` | set | unavailable |
| `device_id` | set | unavailable |
| `platform` | `matomo` | unavailable |
| `area_id`, `name`, `icon`, `hidden_by`, `disabled_by`, `entity_category` | available, unset | unavailable |

*(An early version of this measurement reported "4 of 10 fields lost", which was
wrong: the other six are empty on the native side too, because the **user** has not
set them. The real distinction is "unset but settable" versus "no row to set them
on." Worth stating because it is the kind of error that would survive into a report
unnoticed.)*

## Result 2: no ownership

Native produces **1 config entry and 1 device**. The framework produced **0 and
0** — nothing to reload, reconfigure or delete in the UI, and nothing to group
entities under.

## Result 3: the sharp one — entities did not survive a restart

| | survived an HA restart |
|---|---|
| native | **15/15** |
| framework | **0/15** |

This is not cosmetic. HA restarts a natively-loaded integration itself. REST-posted
states live only in memory, and nothing recreates them.

## The fix: a thin native integration

Three options were on the table: accept and document it; register entities through
HA's WebSocket registry APIs; or **ship a small native integration whose only job
is to own the config entry and device on the framework's behalf.** The third is the
real answer, and it was built.

`spike/bridge_integration/sandbox_bridge/` is ~250 lines. It owns a config entry,
creates one device per sandboxed integration, and exposes a service
`sandbox_bridge.publish` that the supervisor calls instead of posting a state. Its
entities carry a `unique_id` (which is what earns a registry row) and subclass
`RestoreEntity`; the roster of published entities is persisted to disk, so on
startup the bridge recreates them all and each restores its last value.

```bash
./ha_bridge_setup.sh
HA=1 BRIDGE=1 ./run_targets.sh
```

### Does this break the security argument?

No, and it is worth being precise about why, because it is the obvious objection.

**No untrusted code is loaded into Home Assistant.** The sandboxed integrations
still run in their own process, behind the supervisor's manifest checks. The bridge
only ever receives a domain, a key, an entity_id, a state string, and a dictionary
of attributes — and it evaluates none of them. It is a **trusted** component that
belongs to the framework, and at ~250 lines it is small enough to actually review,
which is the property a trusted component must have.

### Result

| | native | framework, raw REST | **framework, via bridge** |
|---|---|---|---|
| entity-registry row | 4/10 set, 6 available | none | **4/10 set, 6 available** |
| config entries | 1 | 0 | **1** |
| devices | 1 | 0 | **1 per integration** |
| **survives an HA restart** | 15/15 | **0/15** | **15/15** |

Across all three targets: **25 registry-backed entities and 3 devices**. The
restart test was deliberately run *without* re-running the supervisor afterwards,
so survival is genuinely the bridge's doing rather than a silent re-publish.

### One difference remains, on purpose

`platform` reads `sandbox_bridge` rather than `matomo`. That is **accurate** — the
bridge is what created the entity — and it makes the sandboxing *visible* in the
UI rather than hiding it. The device is named after the integration and modelled
"Runs outside Home Assistant, under manifest enforcement", so a user can see at a
glance which of their integrations are confined.

### A correction this forced

Result 3 originally supported a strong conclusion: "the supervisor must be a
long-running, restart-aware service." With the bridge holding entity state, that
softens to "should be, for data freshness" — the entities persist regardless. The
measurement changed the architecture, and then the architecture changed what the
measurement implied.

# Part 6 — Where the project stands

## What is proven

| claim | evidence |
|---|---|
| Unmodified HACS integrations can run outside HA's process | 3 integrations, 25 sensors, 69 mediated operations |
| A manifest can confine them | 4 of 5 attacks blocked, with a paired baseline (43 entities readable without, 2 with) |
| **It works against Home Assistant as shipped** | stock 2026.8.1 image, unmodified; 25 entities published into it |
| **Its entities are first-class** | registry rows, config entry, one device per integration, 15/15 surviving a restart |
| The API surface is measured | full catalogue: 3,105 repos, weighted by 1,064,724 real installs |
| Decisions are auditable | hash-chained log detects tampering |

## How much ground it covers — the number to design around

| measure | value |
|---|---|
| executed end-to-end | **3** integrations |
| import-clean, polling sensors | 94/763 (12.3%) |
| import-clean, all patterns | 141/3,075 (4.6%) |
| **share of real installed base** | **1.2%** |
| top 100 most-installed | **1/100** |

The 1.2% is the one that survives a hostile question. **A working mechanism and
almost no coverage are compatible facts**, and the distance between them is
exactly what the measurement quantifies — which is the contribution.

## The gap that is deliberately not hidden

The **adversarial probe** tries five things a malicious integration would do.
Four are blocked — reading an undeclared lock, enumerating the whole house,
calling `lock.unlock`, exfiltrating to an undeclared server. The fifth, reading
`/etc/passwd` directly, **succeeds**, and the probe reports it as a failure
rather than hiding it.

That is the right call. A test suite containing only tests you pass is
marketing, not evaluation. But it is also load-bearing: until filesystem
isolation (namespaces + seccomp) lands, the framework does **not** stop the 2021
file-theft attack, which the plan names as the single strongest result
available. That is now the top open engineering item.

## What the project actually claims

The right question to ask of all this is: *is this just "if Home Assistant were
rewritten to be secure, here is how"?* At 1.2% coverage, someone will ask it.

**No.** The framework requires **zero changes to Home Assistant**, and that is now
demonstrated rather than asserted (Part 4). It is a **retrofit**. Where it is still
vulnerable, and where the report should be candid:

- Users install HACS integrations *into HA's config directory*. Using this
  framework means installing them elsewhere instead — a **workflow change for the
  user**, even though it is not a code change for HA.
- Home Assistant's own "Remote Integration Execution" RFC moves toward process
  separation for non-security reasons. Engage with it directly: this supplies the
  **policy layer** their mechanism would need.

**The accurate one-sentence claim:** *a demonstrated mechanism for confining
unmodified HACS integrations against a stock Home Assistant, plus the first
empirical measurement of what applying it across the real ecosystem would cost.*
Both halves are contributions; the second is the more novel one. That sentence
stays honest at 1.2% coverage. "A sandboxing framework for HACS" does not.

## What this changes for the advisor meeting

- **Lead with the live demo.** Three integrations running against a real Home
  Assistant, entities visible in its UI grouped under devices that say "Runs
  outside Home Assistant, under manifest enforcement."
- **Then the paired security result**, which is the strongest single slide:
  43 entities readable without the framework, 2 with.
- **Decision 3 got harder, not easier.** By repo count polling sensors looked like
  a quarter of the ecosystem; by installed base they are a tenth, and actuators are
  64.8%. Present both numbers. Do not show 24.8% without 10.6% beside it.
- **Bring the coverage curve including the parts that got worse.** Three estimates
  of the shim's size, each revised upward with more evidence (15 → 83 → >120
  symbols). Present as method, not apology.
- **Two anecdotes worth telling**, because both show the methodology catching
  itself: `FrozenOrThawed`, a defect structurally invisible with one integration;
  and the registry gap, found by running one integration two ways and diffing what
  HA thought of the results.

## The one thing still blocked

Everything above was under your control. The advisor meeting is not — it depends on
someone else's calendar, and it gates Decision 3, which determines scope. It is
13 August; the work period starts in September.

Today's work made that meeting considerably more worth having. It did not make it
any less urgent.
