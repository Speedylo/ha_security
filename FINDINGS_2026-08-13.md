# Part 1 — The setting

## What Home Assistant is

Home Assistant ("HA") is free software people run on their own hardware — often a
Raspberry Pi in a cupboard — to control their smart home. It talks to lights,
locks, thermostats, cameras, alarms, energy meters. It is the open-source
alternative to Google Home or Alexa, and its selling point is that your data
stays in your house.

## What an integration is

HA on its own does not know how to talk to your specific brand of doorbell. That
knowledge lives in an **integration** — a small piece of Python code that knows
one device or one online service. HA ships with a couple thousand official ones.

When an official integration is not enough, users install community-written ones
through **HACS** (Home Assistant Community Store), an unofficial add-on store.
There are ~3,105 of them, written by hobbyists, reviewed by nobody.

## The security problem

Here is the part that matters. An integration is **not a separate program**. It
is a Python module that HA loads *into its own process* and hands a live object,
conventionally called `hass`, which is HA itself in memory.

That means a community integration for, say, a broadband quota meter has, by
construction:

- read access to every device state in the house — every lock, camera, motion
  sensor, and whether you are home;
- the ability to call any service — including `lock.unlock` and
  `alarm_control_panel.disarm`;
- read access to `/config/secrets.yaml`, the file where every password and API
  key you have given HA is stored.

Not because anyone granted it those things. Because there is no mechanism to
*not* grant them. There is no permission system. Installing a HACS integration
is trusting its author with your entire house, and this is not theoretical — in
January 2021 HA disclosed exactly this: custom integrations stealing files.

## What the project builds

Two pieces, and the names matter.

**The supervisor** — a trusted program that holds the keys to HA. Every
integration ships a **manifest**, a short file declaring what it needs:

```yaml
name: matomo
publishes:      [sensor.matomo_*]        # entities it may create
reads_entities: []                       # nothing in the house
calls_services: []                       # no actions
network:        [analytics.example.org]  # one host, no others
```

The supervisor enforces that on every single request. Anything not declared is
refused and logged. This is the same idea as phone app permissions — a torch app
that asks for your contacts gets refused — applied where it currently does not
exist.

**The shim** — this is the clever part, and it is the harder half.

The problem: the 3,105 integrations that already exist all begin with
`import homeassistant`. If you run one outside HA's process, that line fails and
the integration dies instantly. So you either rewrite all 3,105 (impossible) or
you make the import succeed.

A **shim** is a counterfeit library with the same shape as the real one. In
Python, `import homeassistant` just means "find a folder named `homeassistant`
on the search path and load it." Control the search path, control what gets
loaded. So the project puts a *fake* `homeassistant` folder first on the path.
The integration calls `hass.states.async_set(...)` exactly as it always has and
cannot tell the difference — but instead of writing into HA's memory, that call
becomes a message on a socket to the supervisor, which checks it against the
manifest.

The integration runs **unmodified**. Not one line changed. That is the whole
trick.

# Part 2 — What was done on 2026-08-13

Two jobs.

## Job A: measure the whole population

The project rests on a bet: *most integrations use only a small, shared slice of
HA's API, so a shim only has to counterfeit that slice.*

That bet had been tested on **200** repositories. The tool
(`hacs_api_surface.py`) downloads each integration and reads its source code
without ever running it — untrusted code is parsed as text, never executed —
recording every `homeassistant.*` name it imports.

A **symbol** is one such name: `DataUpdateCoordinator`, `SensorEntity`. Think of
it as one word of vocabulary the shim must know. The question "how big must the
shim be?" becomes "how many symbols must it implement?"

The tool was run across the **entire catalogue: 3,105 repositories, 3,075 parsed
successfully.**

## Job B: run two more integrations

There was **one** integration proven to run end-to-end. One is an existence
proof — it shows the idea is not impossible. It is not evidence about
*integrations in general*, because the one might have been easy.

Two more were added, chosen because the data said they were closest to working:
`abnvle/ha-matomo` (a web-analytics dashboard) and `aniolpages/ha-icqa` (a
Catalan air-quality monitor). For each: extract the real source untouched, write
its manifest, build a fake version of its cloud service so it can be exercised
without real credentials, and run it.

Both now work. **Three integrations run unmodified under enforcement — 69
permission-checked operations, zero wrongly denied.** `spike/run_targets.sh`
runs all three.

# Part 3 — The findings

## Finding 1: the deep one — a bug that n=1 could not reveal

This is the most valuable thing that happened, and it needs some Python
background.

### Background: dataclasses

A `dataclass` is Python shorthand for "a class that just holds fields":

```python
@dataclass
class Sensor:
    key: str
    icon: str = None
```

You can declare one **frozen**, meaning immutable — once built, it cannot be
changed:

```python
@dataclass(frozen=True)
class Sensor:
    key: str
```

Setting `sensor.key = "x"` on a frozen one raises an error. Frozen is generally
safer; mutable is more convenient.

### The rule that causes the trouble

Python enforces a hard rule about inheritance: **a frozen dataclass may not
inherit from a non-frozen one, and a non-frozen may not inherit from a frozen
one.** Mixing them raises
`TypeError: cannot inherit frozen dataclass from a non-frozen one`. The
reasoning is sound — if a mutable class could inherit from an immutable one, the
immutability guarantee would be a lie.

### Why this bites

HA has a base class, `EntityDescription`, that integrations subclass to describe
their sensors. The shim provided its own copy, declared **not frozen**, with a
code comment saying real HA does something fancier but this was a harmless
simplification.

It was harmless — with one integration. Then:

- **`andrews_arnold_quota`** (target #1) subclasses it with a plain `@dataclass`
  and then *modifies* the object afterwards, rewriting
  `entity_description.entity_id`. **It requires the base to be mutable.**
- **`matomo`** (target #2) subclasses it with
  `@dataclass(frozen=True, kw_only=True)`. **It requires the base to be
  compatible with frozen.**

Now trace the consequences:

| shim's base is… | target #1 | target #2 |
|---|---|---|
| not frozen (what the shim had) | works | `TypeError` |
| frozen | `TypeError` | works |

**There is no choice that runs both.** Not a matter of picking better — the two
requirements are logically incompatible under Python's rule.

### How real HA solves it, and what was built

Real HA uses a **metaclass** — a class that customises how other classes get
created. Theirs is called `FrozenOrThawed`, and the trick is genuinely elegant:
the base class is deliberately **not made a dataclass at all**. It secretly
builds a parallel frozen dataclass off to the side and delegates object
construction to it.

Why that works: Python's frozen/non-frozen rule only triggers when a *base class
is a dataclass*. If the base is not one, there is no conflict to detect — so a
subclass may be frozen or mutable, freely. The base then injects its fields into
each subclass so nothing is lost.

This was reproduced as `spike/shim/homeassistant/util/frozen_dataclass_compat.py`.
One wrinkle: HA's version uses `annotationlib`, a module that only exists in
Python 3.14+, and this project runs 3.12. That part was rewritten to read
annotations directly. Same observable behaviour, runs on the local interpreter.

Both integrations now work, and frozen descriptions correctly *reject* mutation
— so the shim is more faithful than before, not merely more permissive.

### Why this matters far beyond one bug

**A one-integration spike could not have found this.** With one sample, the
simplification looked free. It took a *second* sample to turn it into a
contradiction. The shortcut was not wrong-but-tolerated; it was wrong in a way
that was **structurally invisible** at n=1.

That generalises to every remaining shortcut in the shim. Each is currently
"fine" against three integrations. Some fraction are genuinely fine, and some
are silently incompatible with integration #4 or #12 in ways nothing in the
current evidence can distinguish.

This is the strongest argument for a specific engineering priority: **grow the
number of integrations actually executed**, because that is the only process
that surfaces this class of defect. It is also an excellent thing to tell an
examiner, because it is a *methodological* insight, not just a bug report.

## Finding 2: the sample was biased, and the correction is good news

The 200 repos were taken in catalogue order, which is roughly alphabetical. That
is why every near-miss repository in the old results started with `a`. This had
been flagged as a possible problem. It was a real one:

| pattern | full catalogue | 200-repo sample | drift |
|---|---|---|---|
| actuator (accepts commands) | **46.7%** (1,437) | 58.0% | −11.3 |
| **polling_sensor** (only reads data) | **24.8%** (763) | 15.0% | **+9.8** |
| sensor_other | 9.4% (288) | 13.5% | −4.1 |
| other | 8.0% (246) | 6.5% | +1.5 |
| local_discovery | 7.8% (240) | 6.0% | +1.8 |
| push_stream | 2.4% (75) | 0.5% | +1.9 |
| oauth_cloud | 0.8% (26) | 0.5% | +0.3 |

**Polling sensors — the chosen target — are a quarter of the catalogue, not
15%.** In absolute terms, 763 real integrations rather than the ~285 the old
percentage implied.

This directly strengthens the weakest scoping argument. "I support one pattern"
sounded like a toy restriction at 15%. At 24.8% and 763 real programs, it is a
defensible engineering scope. Actuators (46.7%) are still the larger group and
still where the danger lives — a malicious *sensor* leaks data, but a malicious
*actuator* opens the front door — so that conversation with the advisor does not
disappear. It just starts from better numbers.

## Finding 3: the concentration bet held up

This was the thing that could have killed the project, so it is worth stating
plainly.

The bet was that a handful of symbols covers nearly everything. On 30
integrations, that could easily have been an accident of small numbers. On 763:

| symbol | appears in (n=763) | sample said |
|---|---|---|
| `DataUpdateCoordinator` | 98.7% | 100% |
| `HomeAssistant` | 98.2% | 100% |
| `ConfigEntry` | 96.7% | 97% |
| `SensorEntity` | 93.8% | 93% |
| `CoordinatorEntity` | 93.8% | 93% |
| `UpdateFailed` | 77.3% | 90% |
| `AddEntitiesCallback` | 73.0% | 80% |

The head is slightly less dominant than the sample said — the sample's two
"100%" entries were artefacts of having only 30 data points — but the **shape is
unchanged**. A small core still reaches a large share of the population. Every
downstream decision resting on this survives, now on 763 integrations instead of
30.

## Finding 4: two ways the coverage metric was misleading

The headline compatibility number came from asking: *does this integration
import everything the shim provides?* Two problems, both found on 2026-08-13.

### 4a. Hidden constants made it look better than it was

The measurement tool has a flag, `--exclude-trivial`, that ignores "cheap"
symbols — constants, unit names, type aliases — on the reasoning that they are
trivial to implement. The 200-repo dataset was built with it.

But **a missing constant still breaks the import.** "Cheap to write" and "not
needed" are different claims. `ha-icqa` was recorded as missing exactly one
symbol; when it was run, it failed on
`CONCENTRATION_MICROGRAMS_PER_CUBIC_METER` — a constant the dataset had never
counted.

So the measured gap understated the real gap. Not catastrophically — these *are*
cheap — but any published figure must state which flag produced it.

### 4b. Import success is not an upper bound on compatibility

The docs said import-cleanliness was an **upper bound** — i.e. "at most this
many could work." That claim is wrong, and `ha-matomo` disproves it: **it runs
end-to-end while still counting as one symbol short.**

Why? The missing symbol lives in `config_flow.py`, the module that draws the
setup wizard when a user first adds the integration through the UI. It runs
once, at installation, and never again. Nothing during normal operation touches
it. Missing a symbol there does not stop the integration from working.

So the metric fails in **both** directions:

- **Over-counts:** an integration imports everything, then dies at runtime on
  behaviour the shim does not reproduce — exactly the `current_entry` bug found
  earlier.
- **Under-counts:** an integration is missing symbols that sit on code paths
  that never execute — `matomo`.

It is not a bound in either direction. It is a **proxy**, useful for one job
only: ranking what to build next. The real compatibility measure is
*integrations actually executed* — which is 3, and which is why Job B mattered
more than Job A.

### 4c. A practical trap in the tooling

`shim_coverage.py` must be run under `../.venv/bin/python`. Run under the system
interpreter, `aiohttp` is missing, two shim modules fail to import, and the
scorer reports 180 names and 0/30 — while its warnings go to stderr and the
headline numbers print just as confidently. Worth hardening before those numbers
are quoted anywhere.

## Finding 5: the honest bad news — the cost estimate tripled

A **coverage curve** answers: "if I implement the N most popular symbols, how
many integrations can run?" It is how the size of the shim gets decided.

Measuring behavioural symbols only (excluding the generatable constants), across
all 763 polling sensors:

| behavioural symbols implemented | integrations fully covered |
|---|---|
| 30 | 15.2% |
| **51** | **25%** |
| 80 | 33.9% |
| **120** | **46.1%** (352) |

**50% is not reached within 120 symbols.** The sample had said ~83 symbols would
reach 50%. It does not.

This is now the third estimate of this quantity, and each revision came from
more evidence:

```
~15 symbols    (initial guess)
~83 symbols    (200-repo sample)
>120 symbols   (full catalogue)      <- each correction moved the same direction
```

Three estimates all revised upward is a pattern worth noticing: every time the
question was examined more closely, the job got bigger. That is a reason for
caution about any remaining unmeasured estimate in the plan.

### Why this does not sink the project

Two things stay true:

1. The head of the distribution is still steep — a small core still reaches a
   substantial minority quickly (25% of 763 integrations is ~190 real programs
   at 51 symbols).
2. The expensive tail is dominated by **generatable** material — units, enums,
   selector definitions — that a script can produce from HA's own source, rather
   than hand-written logic. The current top blockers bear this out: `util.dt`
   (blocks 257), the `selector` family (129 and below), `binary_sensor` enums
   (150).

What it kills is the claim *"most integrations run unmodified."* What survives
is *"a small hand-written core plus a generated constants layer runs a measured,
honestly-reported fraction."*

That is a weaker sentence and a stronger position. The advisor is a **security
auditor** — someone whose profession is finding the gap between what a system
claims and what it does. A curve that moved against you, presented as a curve
with its methodology, is far more credible than a single flattering percentage.
Stated limits are an asset with that audience.

# Part 4 — Where the project stands

## What is proven

| claim | evidence |
|---|---|
| Unmodified HACS integrations can run outside HA's process | 3 integrations, 25 sensors, 69 mediated operations |
| A manifest can confine them | 4 of 5 attacks blocked in the adversarial probe |
| The API surface is tractable | 763-integration measurement, concentration confirmed |
| Decisions are auditable | hash-chained log detects tampering |

## The gap that is deliberately not hidden

The **adversarial probe** tries five things a malicious integration would do.
Four are blocked — reading an undeclared lock, enumerating the whole house,
calling `lock.unlock`, exfiltrating to an undeclared server. The fifth, reading
`/etc/passwd` directly, **succeeds**, and the probe reports it as a failure
rather than hiding it.

That is the right call. A test suite containing only tests you pass is
marketing, not evaluation. But it is also load-bearing: until filesystem
isolation (namespaces + seccomp) lands, the framework does **not** stop the 2021
file-theft attack, which the plan names as the single strongest result
available. That is now the top open engineering item.

## What this changes for the advisor meeting

- **Lead with the demo.** Three integrations, running, with a live permission
  trace.
- **Decision 3 got easier.** 24.8% / 763 integrations is a real scope, not a toy
  restriction.
- **Bring the coverage curve, including the part that got worse.** Present it as
  evidence of method, not as an apology.
- **The `FrozenOrThawed` story is the best single anecdote available.** It shows
  a defect found that the earlier methodology was incapable of detecting,
  followed by a fix to the methodology itself. That is the difference between a
  student demo and engineering.

## The one thing still blocked

Everything above is work under your control. The advisor meeting is not — it
depends on someone else's calendar, and it gates Decision 3, which determines
scope. It is 13 August; the work period starts in September.

The work done today made that meeting materially more worth having. It did not
make it any less urgent.
